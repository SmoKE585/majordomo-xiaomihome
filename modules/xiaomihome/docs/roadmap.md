# Что берём из Home Assistant

Для шлюза Xiaomi/Aqara в Home Assistant есть два разных подхода.

| Решение | Транспорт | Сильные стороны | Ограничения |
| --- | --- | --- | --- |
| [`xiaomi_aqara`](https://www.home-assistant.io/integrations/xiaomi_aqara/) | multicast 9898 + ключ | тот же локальный протокол, события | старый формат, мало моделей, требуется ключ |
| [`XiaomiGateway3`](https://github.com/AlexxIT/XiaomiGateway3) | MQTT шлюза после установки агента | push, BLE/Mesh, TTL-доступность | только несколько моделей шлюзов и прошивок |

Наш модуль ближе к `xiaomi_aqara`: он слушает multicast и не требует установки
агента на шлюз.

## Что уже внедрено

- **Тип-aware доступность.** В `XiaomiGateway3` устройство считается доступным,
  пока `last_seen` не старше TTL, зависящего от типа (батарейные — часы,
  сетевые — десятки минут). У нас то же: 15 минут для шлюза, 60 для сетевых,
  65 для motion/cube, 170 для батарейных; порог можно переопределить.
- **Каталог типов и подписей.** Человеческие названия моделей, типы батареек,
  единицы измерения и расшифровка бинарных значений.
- **События вместо опроса.** Значения приходят от шлюза; «Опросить» — только
  разовая команда `read`, как в HA-интеграциях.
- **Диагностика.** Технические сообщения, очередь, последнее событие, ключ и
  IP шлюза видны в карточке.
- **Живое состояние.** Список обновляется без перезагрузки, как в HA-панели.

## Что можно добавить дальше

1. **MQTT шлюза** (как `XiaomiGateway3`) для моделей, где можно поставить
   `openmiio_agent`: это даст push без multicast и поддержку BLE/Mesh.
2. **Ключ из облака** для случаев, когда приложение не показывает LAN-ключ.
3. **Карта типов из базы HA** и автогенерация названий метрик.
4. **Импорт истории** `last_seen` и счётчиков для графиков.
5. **Групповые команды** (включить все реле шлюза) с проверкой ключа.

## Чего не делаем

- Не переносим логику в ядро MajorDoMo.
- Не ставим сторонний агент на шлюз автоматически: это меняет прошивку.
- Не отказываемся от локального протокола ради облака.
